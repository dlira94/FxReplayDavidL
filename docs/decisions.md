| D23 | Elevation is surface lightness plus a 1px border, never shadow | On `--bg-primary` (#030303) a shadow is invisible, and `--card-bg-primary` is the *same* colour as the page background, so a card drawn with brand tokens alone cannot be seen. | D28 | With JavaScript unavailable the header CTA stays hidden, and that is accepted rather than fixed | The stated principle is "no JS → everything visible", and this is its one exception. A no-JS visitor still gets four other primary CTAs, including the hero one immediately below | One element that a no-JS visitor never sees, in exchange for never shipping the wrapped-header regression again. Written down because an undocumented exception to a stated principle reads as a bug to the next person, who then "fixes" it | David |
| D29 | The quiz island runs on Preact via `@astrojs/preact` with `compat: true`, not React | Measured, not assumed: a trivial island (one button, one `useState`) ships **67.4 KB gzip** on React 19 + react-dom, against a 60 KB budget, and that is the floor before the real six-step quiz is added. The same probe on Preact ships **~10 KB gzip**. The 57 KB difference is not spent on a marketing page a visitor might never interact with — it is spent **at the exact moment someone decides to sign up**, on whatever connection they happen to have. A budget that only measured pre-interaction JS was measuring the cheap half of the page, so CLAUDE.md now carries a second one: under 25 KB gzip for the island on open | `compat: true` aliases react/react-dom to preact/compat, so the island is written as ordinary React and imports from `'react'`. Going back to React is a one-line config change rather than a rewrite, which matters because CLAUDE.md named React as the stack and a real production team may have reasons to keep it. The residual risk is third-party React libraries that compat does not cover; the quiz uses none | David |
| D30 | The shared Zod schemas are built on `zod/mini`, not the classic entry point | Classic Zod's builder API does not tree-shake: importing three schemas into the quiz island pulled in ~80 KB raw and put the island 67% over its 25 KB budget. Mini is the same library and the same validation, exposed as functions, so only the checks actually used get bundled | The functional API is wordier — `z.string().check(z.minLength(1))` instead of `z.string().min(1)` — and unfamiliar to anyone who has only used classic Zod. Worth it: the alternative was hand-written client validation that could silently drift from the server's, which trades a correctness guarantee for kilobytes. CLAUDE.md's "validate with the shared schemas on both client and server" survives intact | David |
| D31 | e2e splits by what it is testing: interface behaviour runs against **mocked** API responses, database behaviour has **dedicated** tests | A UI test should fail when the UI is wrong and for no other reason, so `page.route()` makes the network deterministic. **One** e2e still runs the full happy path against the real database, so island → endpoint → Postgres is genuinely exercised; the other 13 integration tests call the handlers directly. Suite time went from ~90s to ~15s, which matters more than it sounds: a slow suite gets run less often | Mocked responses can drift from what the API actually returns. Two things hold that line: the integration tests assert the real shapes, and the mocks return the envelope from `api.md` rather than an invented one. **Note on why the tests were flaky in the first place:** the original diagnosis — Neon latency — was wrong. Two real causes were found by measuring instead: Astro server-renders an island's markup and hydrates it after, so the inputs were visible and inert while the tests clicked them; and `useEffect` is deferred, so the step painted before the code that saved it ran. Mocking was the right structure regardless, but it was not the fix |
| D32 | `.quiz` carries a `min-height` equal to the tallest step | On a reload mid-quiz the server renders step 1 — it cannot read `sessionStorage` — and hydration swaps in the restored step about 250 ms later. Measured at 390 px: step 1 is 371.9 px, the tallest step is 527.3 px, and that 155 px growth measured **CLS 0.069** against a 0.05 budget. Lighthouse scores 0 on this page because the shift needs a returning visitor with a saved session, so nothing in CI would ever have caught it | A floor of 33 rem leaves empty space under the shortest step on a first visit. Accepted, and it buys something beyond the metric: the card stops resizing under the visitor's thumb at every answer, which the page below it was doing on every step. The restore can only land on steps 1–6 — `done` is not persisted — so the result screen being taller (698.8 px) does not reopen the gap | David |
| D33 | The quiz keeps only the **first name** in `sessionStorage`, never the email, and clears the whole saved state the moment the quiz completes | Two principles, applied literally: **the minimum personal data, for the shortest time.** The name earns its place — the result title is "{name}'s practice plan", so losing it means showing a plan addressed to nobody. The email earns nothing: a visitor who reloads at step 6 is looking at the email field and retypes it in seconds, so storing it would be holding personal data for no benefit. And once the quiz is done the record is in Postgres, so the browser copy has no reason to outlive it — it is deleted rather than left to expire with the tab. The alternative to storing anything, refetching from the server on every mount, would need the record readable by id, which is exactly what the edit-token design refuses | A reload at step 6 costs the visitor retyping their address. Accepted: that is the point. "PII lives only in Postgres" (CLAUDE.md) still reads stricter than what ships for the duration of the quiz, so it is written down rather than left for a reader to file as a violation | David |
| D34 | GA4 `client_id` / `session_id` are read from the `_ga` cookies and stored on the user, and the server accepts them as **null** | GTM loads deferred (D10), so a fast visitor reaches quiz step 1 before the cookies exist. Rejecting the signup, or waiting for GTM, would trade a conversion for a reporting field. Instead the columns are nullable, the conversion PATCH attaches them if they arrived by then, and they are never overwritten once set | A conversion from someone who converted before GTM loaded reaches GA4 without session attribution, or not at all — `sendAccountCreated` refuses to invent a `client_id`, because a random one creates a phantom GA4 user that matches no real session, which is worse than a missing event. Postgres still has the signup either way, and Postgres is the source of truth for the readout (D17) | David |
| D35 | `account_created` is sent server-side, behind `waitUntil`, and stamped in the database once delivered | It is the numerator of the only metric that decides anything, so it cannot depend on the browser surviving long enough to fire a pixel. `waitUntil` keeps it off the response path: the visitor gets their plan whether or not Google answers. The `account_created_sent_at` stamp makes "exactly once" a fact in a row rather than a property of control flow — the status transition already happens once, but a stamp survives a refactor that the reasoning does not | A delivery failure is logged and the signup is kept; the request never fails over a reporting call. **QA conversions are sent too**, carrying `is_qa: true`, and excluded in GA4 reports rather than at the send — skipping them made the event unverifiable, because the only way to test a real conversion before shipping is a QA one. Same rule as bots (D18): recorded, flagged, excluded in analysis, never dropped at the door. The payload is validated against GA4's `/debug/mp/collect` in an integration test, because the production endpoint answers 204 to malformed events and drops them in silence | David |
| D36 | The dashboard authenticates with a POST form and a hashed session cookie; the admin token never appears in a URL | A token in a query string ends up in server logs, in the `Referer` header of anything the page links to, and in browser history — three places nobody thinks to clear. The cookie holds a SHA-256 of the token rather than the token, so a stolen cookie opens the dashboard but not the API. `httpOnly`, `Secure`, `SameSite=Strict` and an 8-hour expiry | One more surface to maintain than a bearer header alone, and the token is still a single shared secret rather than real accounts — acceptable for an internal readout, and `api.md` already records real auth as a production change. Astro's CSRF origin check rejects the POST without a matching `Origin`, which is why `curl` needs `-H Origin` to log in and a browser does not | David |
| D37 | `/api/stats` returns counts only and is what the dashboard and the `growth-analyst` agent read; `GET /api/users` stays the single PII surface | "The agent must not print emails" is a rule that can be broken. "The agent cannot see emails" is a property of the system. The stats response has no name, no address, no anonymous id — an integration test asserts the exact key set per variant, so adding a leaky field is a failing test rather than a code review someone has to catch | Two endpoints where one would do, and the aggregates have to stay in step with `analytics.md` §5. In exchange the only endpoint that can leak a person has exactly one consumer and one reason to be called | David |
| D38 | The dashboard reads `GET /api/users` over HTTP and masks emails on the server before render | The challenge requires create, update **and list**, so the listing needs a real consumer rather than an endpoint nothing calls — an untested contract rots. Fetching it the way a separate front end would keeps it exercised on every dashboard load. Masking happens server-side, so the full address never reaches the DOM: not hidden with CSS, not truncated in the browser. A screenshot of this page in a review, or a shared screen in a meeting, is not a customer list. Names are not rendered at all | One internal HTTP round trip per dashboard load, where calling the query directly would be free. Worth it: it keeps the endpoint honest, and the masking boundary is on the side of the wire where it cannot be undone by a devtools inspector | David |
| D39 | The dashboard states a decision per arm — Ship / Continue / Reject / Invalid — and holds **Continue** until every arm reaches the required sample | The rules in `experiment.md` exist so the call is made before the data arrives. A dashboard that shows a winning interval without saying "this is not a decision yet" invites exactly the thing the rules forbid: stopping on a lead that appeared early, which is how an A/B test manufactures a result. So the verdict is on screen next to the number, and the early-lead caveat is visible rather than in a document nobody opens mid-review | The decision uses the Bonferroni-corrected α = 0.025 while the table shows the 95% interval people expect to read, so an interval can look clear of zero while the status still says Continue. That gap is deliberate and the reason text says which is which | David |
| D40 | The GTM loader captures pointer and key events but listens for `scroll` **without** capture | `scroll` does not bubble, but a capture-phase listener on `window` still sees scrolls from every descendant — and the testimonials rail (`overflow-x: auto` with `scroll-snap`) emits one at layout, with no user input, settling at `scrollLeft: 16`. That counted as "first interaction" and pulled 123 KB of `gtm.js` into the critical path: requested at 531 ms against a first paint at 568 ms. Above 48 rem the rail stops scrolling, so the bug existed only on the primary form factor and only below a breakpoint | Losing capture on `scroll` means a scroll inside some future scroll container will not count as intent. That is the correct reading anyway: scrolling a carousel is not intent to open analytics. Measured cost of the bug was nil — LCP 1,655 ms with GTM, 1,874 ms blocked — so this was fixed because D10 is a promise, not because a number hurt | David |
| D41 | In the quiz, selecting and advancing are separate actions: a tap or click does both, arrow keys only select, and Enter, Space or a visible "Continue" button commits | In a radio group the arrow keys move focus **and** check the option, so advancing on `change` meant a keyboard user could not read option 3 without having submitted option 2. That is WCAG 3.2.2 (On Input) — a change of context on selection — and it is also just hostile: the person least able to undo a mistake was the one it happened to. A pointer still advances, so the one-tap flow `experience.md` §2 asks for on mobile is unchanged | A `pointerdown` flag distinguishes the two, which is a small amount of state to carry. The alternative — inferring intent from whether a `click` event accompanied the `change` — depends on browser behaviour that differs across engines for arrow-key selection | David |
| D42 | `quiz_start` fires on intent, once per session: a CTA click, or the first focus or keystroke in the name field | It used to fire when the island hydrated. The quiz is **inline**, not a modal, so that counted every visitor who scrolled to the bottom as a start — the intent stage measured "reached the footer", and the start rate was inflated by everyone who never touched it. Found by David in Tag Assistant, where `quiz_start` arrived *before* `cta_click` with a scroll between them | A programmatic focus has to be excluded explicitly, because the island focuses its own input on mount and would otherwise re-create the bug one line lower. Start rate will drop when this ships; the new number is the real one and the old series is not comparable to it | David |
| D43 | When GA4's `_ga` cookies do not exist yet, `account_created` is sent with a `client_id` **derived from `anonymous_id`**, and delivery is retried with backoff | GTM loads deferred (D10), so a visitor who converts quickly has no GA4 client id, and the event was simply dropped — silently, permanently, and precisely for the fastest-converting visitors, which is a biased hole rather than a random one. A derived id is stable per visitor, so a retry cannot invent a second GA4 user | The conversion is counted but **loses session attribution**: it does not join the browser session, so source/medium for that user comes from the stored `utm_*` fields instead. Counting it wrong beats not counting it, and the server logs every derived-id send so the rate is knowable. Retries are 0.5s/2s/6s inside `waitUntil`; a 4xx is not retried, because a malformed payload stays malformed | David |
| D44 | The quiz moves focus only when the visitor arrives by intent, never when the island mounts by scrolling | The island hydrates on `client:visible`, so it mounts when the section enters the viewport — not when anyone asked for it. Focusing the name field then takes focus from someone who is only reading: on a phone it opens the keyboard and jerks the scroll, and a keyboard user is thrown out of their place in the page. Arriving by CTA is different: that *is* asking to start, so focus moving there is what was wanted | The CTA sits above the fold and the island hydrates below it, so the island cannot hear its own entry click — it does not exist yet. The inline script leaves `data-quiz-intent` on `<body>` and the island reads it on mount. One more piece of state crossing the hydration boundary, for a focus behaviour that is otherwise impossible to get right | David |
