| Sep 18 | Claude Code | **Accepted with correction** | Build masked text entrances driven by IntersectionObserver | **The bug that produced no error.** Twenty-two elements rendered invisible and stayed that way: no build error, no type error, no failing test, no console output. The CSS was valid, the script ran to completion, and the observer was correctly wired to every element.<br><br>**The cause:** the hidden state used `clip-path: inset(0 0 105% 0)`, which shrinks an element's *intersection rectangle* to zero area. `IntersectionObserver` therefore reported `isIntersecting: false` forever — and the only thing that would have removed the clip was that observer's callback. The mask blocked its own reveal. A deadlock with no symptom except absence.<br><br>**Wrong hypothesis first, corrected:** Claude's initial read was that the CSS rule was not applying, because adding `is-visible` by hand left `getComputedStyle` reporting the hidden value. That was a bad test — `clip-path` carried a `transition`, so reading the computed style in the same frame returns the *starting* value. It said so rather than quietly moving on, and went looking again.<br><br>**How it was isolated:** a side-by-side control in the live page — two sibling elements, one observer, identical options, identical scroll position, `clip-path` removed from one. The clipped element reported `ratio: 0, isIntersecting: false`; the unclipped one reported `ratio: 1, isIntersecting: true`. One measurement, no ambiguity left.<br><br>**Fix:** `mask-image` instead, which is a paint effect and leaves the layout box alone — same wipe, no deadlock. Plus an e2e assertion that after a full page scroll no `.reveal` may still be missing `.is-visible`, because this failure mode is invisible to every check that is not a browser. Same lesson as the header-CTA scoping bug: silent CSS needs a browser, not a type checker |
